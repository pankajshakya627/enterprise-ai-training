Engineering / application walkthrough

Inside NexaAssist: from policy evidence to an approved action.

An assistant can explain a policy, look up an account and prepare a service request. Each task needs a different boundary. Here is how the current NexaAssist application connects them.

19 November 2026Based on reviewed sourceSynthetic banking environment
What this article covers.

The running application checkout and its companion banking source, including uncommitted work. This is an explanation of implemented behavior. The production-hardening plan and live deployment certification are separate.

Start with the job, not the stack.

A staff member asks, “What is the maximum loan amount for NexaHome?” Another asks for the accounts and loans belonging to an authorized customer. A third wants to prepare a home-loan enquiry case. Those requests can share a chat window, but they should not share the same execution path.

The policy question needs evidence that applies to the selected policy date and product. The customer read needs an authorized scope and a typed bank response. The case request needs complete fields, validation, a durable proposal and a different reviewer before execution.

NexaAssist brings these paths together through a Streamlit interface, two FastAPI applications, LangChain chains, a LangGraph workflow, MongoDB Atlas and scoped MCP adapters. Its present banking environment is synthetic. It does not make credit decisions or provide investment, tax or legal advice.

  1. INTERFACECapture the request
  2. EVIDENCEFind policy or facts
  3. CONTROLValidate and authorize
  4. OUTCOMEReturn an answer or receipt

Three local processes, distinct responsibilities.

Streamlit renders the interface. It sends requests to the APIs, shows answers and evidence, and keeps browser-session state. It does not define retrieval chains or query MongoDB directly. Normal reruns retain the current chat and sign-in; a hard refresh or process restart can reset session-only history.

The Agent API coordinates intent and actions. It resolves access, routes requests through LangGraph, calls the configured policy retrieval adapter and banking tools, and manages saved runs. Classification and grounded policy answering use configured model clients within the Agent process.

The RAG API owns the policy retrieval and direct-answer service. It provides retrieval, cited answers, optional answer evaluation and feedback routes. Agent policy chat normally retrieves evidence through policy MCP, then generates its answer inside Agent. It does not simply proxy every question to the RAG answer endpoint.

The deployed-banking profile keeps these three processes local. It connects banking operations to the hosted Horizon MCP endpoint and the Render banking API. Local banking and direct HTTP compatibility are explicit profile choices; they are not automatic failover paths.

A policy answer starts with a dated corpus.

Retrieval embeds the question and searches MongoDB Atlas. The current scope uses institution, effective dates, jurisdiction, confidentiality metadata and optional product. Dense retrieval is selected in the reviewed deployed profile. Hybrid search and reranking are configured alternatives.

The first matches are child chunks. Where a matching parent exists and its metadata is consistent, the chain expands the result to the full section. Missing or inconsistent parents can fall back to child text. The retrieval layer also resolves applicable linked amendments and reconstructs their content.

The answer chain assembles bounded context and checks that required amendments have not been lost to the context budget. If one is missing, it returns insufficient evidence before generation. Otherwise a configured chat model creates a structured answer draft.

Before release, inline citation IDs must match the evidence references, every referenced source must be known, and each quoted passage must occur exactly in the retained source text. There are at most two citation attempts. If validation still fails, the chain returns insufficient_evidence. The current UI receives a completed answer; it does not receive provisional answer tokens.

Scope is not identity authorization.

These corpus metadata filters are not per-user document ACLs. Public retrieval and policy-answer routes in this checkout do not implement the planned staff OIDC and document-access manifest.

A customer read follows an authorization path.

Consider “Show the accounts and loans for customer NXC-0010.” The customer ID identifies the requested subject; it does not grant access. In the UI, the staff member signs in using their own named Agent credential. The session endpoint resolves a stable principal, permitted customers and reviewer permission.

With MongoDB staff authentication selected, the application stores one-way SHA-256 verifiers of high-entropy random API keys and current grants. It reads enabled, institution-scoped records. A revoked key or a staff-store failure does not switch the application to environment grants. This is API-key authentication, not staff SSO.

The customer-context service checks the resolved customer scope and supports accounts/loans, disclosed income with verification status, and bounded transactions for owned accounts. Transaction queries resolve and verify an account before requesting a page, validate dates and limits, and check the returned scope.

These reads return typed factual results. They do not create bank records and do not require a write proposal. Other customer tools may exist in MCP without being connected to Agent chat.

Compatibility detail: an explicitly configured legacy environment training token can still provide scope to one-shot API reads. The UI session portal and durable saved-run routes require named identities. Do not treat that compatibility path as staff SSO.

A proposal is not a completed banking action.

Now consider “Prepare a LOW-priority LOAN_ENQUIRY case about home-loan documents for NXC-0010.” The workflow checks that the action is supported, the customer is authorized and required fields are present. It retrieves dated evidence and validates the request against policy and required banking facts.

An allowed result becomes a durable saved proposal. The run stores its owner, an exact proposal hash and one stable operation key. LangGraph pauses at an approval interrupt. The interface shows the proposed payload and evidence so that a different authorized reviewer can approve or reject that exact proposal.

The service prevents self-approval. Review permission and customer scope are server-managed. Approval is time-bounded; the default expiry is fifteen minutes from run creation, rather than fifteen minutes after a reviewer happens to open the page.

Approval resumes the workflow, but it does not skip validation. Policy and banking facts are refreshed. A changed proposal or policy fingerprint blocks execution and requires a fresh proposal. Current owner and reviewer grants, the retained banking identity, the safe retry boundary and the execution lease are checked before the external write.

Read the outcome literally.

A created-case receipt confirms that case creation was observed. A service-request receipt confirms acceptance and does not necessarily mean the requested downstream work has completed.

The separate-review flow described here is the durable UI workflow. The legacy direct-submit route is disabled by default. Explicitly enabling AGENT_ALLOW_DIRECT_SUBMIT creates a separate compatibility path without that durable review flow.

MCP gives each integration a constrained interface.

The application has two distinct MCP roles. Policy MCP is a read-only stdio child exposing retrieve_policy, a retrieval-contract resource and an explanatory prompt. It wraps the RAG HTTP retrieval endpoint; it does not access the bank or query Atlas directly.

Banking MCP exposes a fixed twelve-tool contract. The application adapter maps known banking operations to those tools. Hosted requests carry Horizon OAuth and an application-signed context binding the principal, customer scope, backend identity and short expiry. Writes also need a grant bound to the exact tool, canonical arguments and original operation key.

Three credentials serve different purposes: the staff key resolves application authority, operator OAuth authenticates to the gateway, and the backend bank bearer authenticates MCP to the bank API. Signing in to Horizon alone does not authorize an Agent banking write.

The companion repository also includes an optional Claude stdio approval bridge. That bridge uses its own explicit human-confirmation model; it is not the same authority flow as the application’s separate staff reviewer.

Uncertain outcomes keep their original identity.

A bank can commit a write even when the application loses the response. Treating every timeout as “nothing happened” risks duplicate submissions. The run service records the first attempt before the effect and retains an unconfirmed run when the result is ambiguous.

Recovery loads that same saved run. A retained submitted result is returned without replaying the action. An eligible uncertain run reuses the exact payload and operation key within the safe retry window. The application’s boundary is twenty-three hours; the companion bank’s idempotency window is twenty-four hours.

The companion bank commits mutations, counters and replay results in one MongoDB transaction. Within the window, a matching operation can return its original replay receipt. Reusing its key with another payload is rejected. A changed bank destination or expired safe window requires reconciliation, not a replacement key.

The local mock bank behaves differently: its write and replay state live in process memory. Restarting that mock is not equivalent to restarting the persistent Render service.

Small wording changes matter: a note is still a note.

The request “add this note: please take this on high priority” appends text to an existing authorized case through the reviewed-write flow. It does not update the case’s priority, escalate it or promise a response time. The application checks case ownership and does not create a replacement case if the referenced one is missing.

Fixed structured note text is excluded from routing-model variables. Unstructured query text can still be classified. Stored bank notes are not fed back to the model as authoritative instructions. These distinctions reduce unintended instruction paths, but they do not establish a complete production privacy or prompt-injection guarantee.

Data ownership extends beyond the vector index.

Application MongoDB holds child vectors and full policy parents, feedback, current staff grants, run metadata and LangGraph checkpoints. The companion bank owns cases, service-request receipts, counters and idempotency records. They are distinct logical storage responsibilities and may share a cluster.

The authoritative document register controls policy ingestion. Changed child chunks are embedded and upserted, parents are updated, and stale records are removed. This happens in place across collections. The current implementation does not publish an immutable paired corpus generation, and retirement physically deletes scoped records rather than retaining rollback-safe tombstones.

Operational run/checkpoint retention defaults to seven days. That is not an independent, insert-only, year-long action audit. The manifest and diagrams describe this distinction explicitly.

Quality evidence and release readiness are separate.

The project uses linting, formatting, types, floor guards, tests, coverage and source/secret scanning. The retained application coverage floor is 84.13%; changed application lines require 100%. Quality and security baselines must not be weakened to obtain a passing change.

Live answer evaluation uses the retained golden dataset, RAGAS metrics and structured judges with protocol fingerprints and metric floors. It is separate from source tests. The trusted live workflow is manual or callable; a versioned production release bundle and enforced promotion/rollback process are separate hardening work.

Datadog tracing and scored exports are configurable, and structured JSON logs are available. Current LLM annotations can still contain question, context, answer and prompt variables. Metadata-only production export, provider/data-class approval and verified external receipt require additional evidence and controls.

The same standard applies to this article: rendered diagrams and verified source paths do not prove deployed-image parity, staff SSO, global capacity limits or production readiness.
